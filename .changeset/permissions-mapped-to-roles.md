Roles can now grant permissions, and access tokens carry them (#415, ADR 0004). An admin manages the catalogue with `GET` and `POST /admin/permissions` and `PATCH` and `DELETE /admin/permissions/:permissionName`, reads roles with `GET /admin/roles`, and replaces what a role grants with `PUT /admin/roles/:kind/:roleName/permissions`. Each write needs step-up and is audited. Deleting a permission a role still grants answers 409 with those roles. Instance roles stay in `available_roles`, and removing one also removes its mappings, so adding the name back later does not restore old grants. Access tokens gain a `permissions` claim, matched exactly with no wildcards or implied grants, which is empty on a recovery session. When the permission claims would pass 1 KiB, which keeps an adapter's session cookie under the browser limit, the token instead carries `permissions_omitted: true` and a guard reads `GET /users/me/permissions`, which answers from the database on every call. `GET /users/me` gains `user.permissions`. Changes reach a token when it is next issued, within the access token lifetime. New migration adds the `permissions` and `role_permissions` tables.

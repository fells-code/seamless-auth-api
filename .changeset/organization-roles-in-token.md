A backend can authorize per organization from the access token alone (#416, ADR 0004). Inside an active organization, tokens gain `org_roles` and `org_permissions` beside `org_id`, and `GET /users/me` and `GET /users/me/permissions` report the same. Organization roles never appear in `roles`, so a guard on `admin` does not pass for an organization admin. Organization roles are now a catalogue, managed with `POST /admin/organization-roles` and `PATCH` and `DELETE /admin/organization-roles/:roleName`, listed by `GET /admin/roles`, and mapped to permissions with `PUT /admin/roles/organization/:roleName/permissions`. A new migration seeds it with the built-in `owner`, `admin` and `member` and every value memberships already hold, and rewrites no membership. **Behavior changes:** assigning a role outside the catalogue now answers 400. `PATCH /organizations/:id/members/:userId` now needs step-up. Only an owner or an instance `admin:write` can grant or remove `owner`, or remove an owner from an organization, and any other manager can only grant a role whose permissions they hold, so an organization admin can no longer make themselves owner. Adding, changing and removing members is audited as `organization_member_added`, `organization_member_updated` and `organization_member_removed`, and a refused change as `organization_member_role_grant_refused`. **Fixes:** removing a member now reaches the token. Previously every refresh copied `org_id` from the session until it ended. Now the next token drops the organization claims and the session stops naming the organization. Recovery tokens carry no organization claims.
